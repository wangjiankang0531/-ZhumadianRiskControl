# 受控启动器选择源码重建的平台辅助组件

原平台辅助组件已经能够从项目源码重建。本阶段把产物接入受控启动器，允许下一实例显式使用这些组件，替代对应的旧实验编译目录。现有 j14 继续运行其冻结启动器，不进行热替换；本阶段没有启动新的原应用组合或进行公网发布。

## 选择和安装

serve_original_integrated_candidate.py 新增 --platform-support-receipt 与 --platform-support-sha256，必须成对传入构建输出的 receipt.json 和构建侧保存的可信 SHA。参数形状在工作区/持久锁/组件创建前验证；随后 build_original_platform_support.select_support 验证产物，再进入原有业务选择与前次正常退出检查。

选择器只需本工具、项目可信 original_platform_support.lock.json、输出目录和显式可信收据 SHA，不读取参考源码、原平台大 JAR、旧准备收据或私有编译输入路径。要求成功构建、合法 owner、固定锁、21 个 class 逐 SHA 相同，观察 JAR 恰含 12 class 与固定 spring.factories，共 13 个成员。精确检查普通文件/目录集合、日志边界和额外成员，拒绝重解析点。Windows javac 可能留下 tmp/hsperfdata 用户目录；仅接受最多一个空目录，不允许任何内部文件或子目录，也不将它加入类路径。

启动器复制 8 个包装 class 和 1 个配置 builder class 到新实例，复制后与可信预期 SHA 再次比对，避免依赖源目录后续变化。新分支使用普通副本，不与构建目录保持硬链接。观察 JAR 在叠加当前实例辅助类前再次核对 SHA。未传新参数时仍使用既有准备目录和硬链接方式，原平台/业务的启动顺序、认证、数据与持久文件门槛保持现有逻辑。

```text
python -B tools/serve_original_integrated_candidate.py <既有显式配置、唯一新编号与真实前次正常收据等参数> --platform-support-receipt <已验证构建输出/receipt.json> --platform-support-sha256 <构建侧可信SHA>
```

本参数可与已验证的独立业务载荷参数组合。它只解除这一组平台辅助产物对旧实验目录的运行依赖；整体控制器仍读取原平台归档、JRE、数据库、Redis、对象存储、前端和现有运行元数据，尚不是独立服务器完整包。

## 实际检查

23 项构建/运行选择与实际错误 CLI 检查通过，包含额外或缺失 class、文件内容变动、观察 JAR 成员/入口替换、复制过程中损坏及选择后 JAR 变化；后两项直接执行控制器对应的复制/检查 AST。另 22 项独立业务检查、22 项参考运行件检查（含 5 DTO 契约）通过，未为这些检查重复启动原应用或数据库。

真实预检选择上一轮独立构建产物，执行控制器的选择表达式两分支、9 class 复制循环和观察 JAR 叠加代码。9 个副本逐 SHA 同且确认不是硬链接；观察 JAR 的 13 个成员字节同。基于选中的包装类，按实际配方重新编译 3 个持久文件启动 class，逐 SHA 与当前 j14 一致。隔离 Python -I 只放工具与锁后真实选择通过。没有重复构建 134 MiB 业务载荷、原平台大 JAR、GIS 或数据库。

首次预检在创建安装文件前拒绝了编译器留下的空 hsperfdata 目录。该失败记录保留，明确接受 tmp 下单个空性能目录后通过，非关闭额外 class/路径检查。随后增加复制后的固定 SHA 及打开观察 JAR 前复核，最终预检再次通过。

## 交付边界

当前 j14 的冻结控制器尚不含新选择参数，它使用的是此前编译的同字节组件。不能把预检、字节一致或源码接线说成整套新组合启动通过。新实例仍须在 j14 真实正常退出、六组件/ContextClosed/持久锁等收据核实后，按唯一新编号启动；j14 自有持久探针与标记保留，下一次恢复必须匹配该次真实收据，不能复用更早已消费标记。

完整服务器运行配方与依赖/数据持久化、原账号登录后的全模块操作、附件、手机真机、IIS/TLS 与公网同版仍待验收。正式 8767 与公网保持原状，fullCloneReady=false。无新增数据库字段、索引、状态或归属。Git 仅同步自有工具/控制源码、测试及本说明，不含私有构建收据、原配置/源码/JAR、依赖、数据库、业务行、凭据或其他未完成修改。
